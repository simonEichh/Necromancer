# Necromancer

Roblox idle/gacha game ("Necro Buddies"). Players buy and dig graves to roll undead units (gacha), place them on grave slots on their plot, and the units march down a lane breaking walls for gold and upgrade materials. **A run is 32 walls standing in the lane; the army advances to the next wall after each break; the last wall is THE GATE; breaking it unlocks ascending (no gold price).** Ascending resets the run (wall, gold), multiplies all unit damage by 1.5, unlocks the next grave tier and one more grave slot (5 + ascensions, max 10), and puts the player back in the plaza. Units can be upgraded in the Forge with materials the walls drop. 9 ascensions, grave tiers Mossy..Celestial, 9 rarities Common..Primordial. Design inspiration and the wish list live in `Notes.txt` (a "Spin a Baddie"-style game).

## Workflow

- Code is synced with **Rojo** (`default.project.json`, `rojo serve`). The repo in `src/` is the source of truth for all scripts. Never edit scripts directly in Studio, and don't use the Studio MCP to write script source that Rojo owns.
- The world (Plots, Shops, HubFloor, models in ServerStorage) lives only in the Studio place file. Use the Roblox Studio MCP to inspect or change it.
- Rojo mapping: `src/server` -> `ServerScriptService.Server`, `src/client` -> `StarterPlayerScripts.Client`, `src/shared` -> `ReplicatedStorage.Shared`. `init.server.lua` / `init.client.lua` make the folder itself the script, so sibling files become its children (`script.Modules.X`).
- Test with the Studio MCP: start play mode, read console output, then stop. Check `get_console_output` for errors after every change.
- Commit one feature per commit, with a clear message. Only commit when asked. End commit messages with the `Co-Authored-By` line the session asks for.
- **The user's preferences:** small incremental steps (limited credits: do not over-explore), dark gothic UI, **no emojis anywhere in the UI**, no special treatment per rarity until the top rarities are settled, models/features are approved batch by batch, they test in their own Studio and often ask for visual tweaks after seeing something. Keep replies short and say plainly what is not done/untested.
- **Studio MCP tips:** `execute_luau` needs `datamodel_type` (`Edit`, `Server` or `Client`; Edit is not available while playing) and only returns what you `return` (prints go to `get_console_output`, which dumps the whole log). `require` inside `execute_luau` gives FRESH module instances (not the running game's state), so inspect state through the instances in the DataModel, not by requiring game modules. Client `execute_luau` can fire remotes (`ReplicatedStorage.X:FireServer`); server `execute_luau` can `FireClient`. `screen_capture` needs a `capture_id` string and works (the Studio window must not be minimized); `user_keyboard_input` takes `actions` like `[{"type":"key_press","key":"F"}]` but is unreliable, so prefer firing remotes or setting `Visible`. After editing scripts wait ~10 s (Rojo sync) before starting play, otherwise the play session runs the old code (check with `Source:find(...)`). Long build scripts can be run without pasting them: serve `tools/studio` with `python -m http.server 8765 --bind 127.0.0.1` and in Edit mode `loadstring(game:GetService("HttpService"):GetAsync("http://127.0.0.1:8765/<file>.lua", true))()` (needs Game Settings > Security > Allow HTTP Requests, which the user turned on). Large Lua/Python edits: write a patch script file to the scratchpad and run it (long heredocs in the shell break), keep tabs exactly (check with `cat -A`), and use the Edit tool for single replacements.
- **Resetting the user's test save** (done after most test sessions): in Edit mode `game:GetService("DataStoreService"):GetDataStore("PlayerData_v1"):RemoveAsync("player_7135437538")`. Test saving with `Player:Kick()` from a server `execute_luau`, stop play, then read the key back in Edit mode. Dev units never save.
- **Publishing**: the world, models and the `ReplicatedStorage.UnitModels` copy live only in the place file: save the place (Ctrl+S) and run `tools/studio/publish_unit_models.lua` after model changes; File > Publish to Roblox; set the experience Private/Friends for testers. DEV panel and `/give` only work in Studio. `Workspace.ModelPreviews` was deleted (rebuild with `tools/studio/show_previews.lua` if needed).

  - **The army advances down the lane to the gate.** A run is `Economy.WALLS_PER_RUN` = 32 walls that ALL stand in the lane from the start (`Walls.lua`: first wall at `WALL_FWD` 105, last wall = THE GATE at `GATE_FWD` 302 right in front of the outer ring's gate tower, `WALL_SPACING` about 6.4 studs, 20 high, thickness 3; the gate is 36 high, bronze, thicker). `plotState.wallQueue[layer]` is the wall of that layer. ## Architecture

**Server** (`src/server/init.server.lua` is a thin bootstrap: player lifecycle + Heartbeat loop). Logic lives in `src/server/Modules/`:
- `Remotes` (creates every remote), `PlotRegistry` (shared `playerPlots`/`getPlot`)
- **`PlayerData`** (authoritative gold/gems/inventory/graves/upgrades/ascension per player, with `changed` -> coalesced `DataSync` snapshot to the client), **`Persistence`** (DataStore load/save/autosave/BindToClose), `Inventory` (SellUnit/SwapInventory/RequestData handlers)
- `Plots` (claiming, grave slots, ascend), `Walls` (HP bar, preview queue, break/reset), `Army` (spawn/recall/placement handlers + unit AI)
- `UnitUpgrades` (the Forge: UpgradeUnit/DismantleUnit), `Rolling` (rarity/unit rolls from the grave's own odds table, pity), `Digging` (DigGrave handler), `Wheel`, `Quests`, `Upgrades` (purchases), `GraveShop` (stock rotation + purchases), `ShopNpcs` (NPC prompts), `DevTools` (Studio-only: spawn any unit at your wall for testing, see below)
- Dependency order (no cycles): Remotes -> PlayerData -> PlotRegistry/Quests/Upgrades/Rolling/Wheel/GraveShop -> Walls -> Army -> Plots/Persistence/UnitUpgrades. Modules attach their own remote handlers when required.

**Shared data** (`src/shared`, `ReplicatedStorage.Shared`): `Units` (stats, rarity pools, emojis, `getBaseOneIn`), `Graves`, `Rarities`, `Economy` (costs, sell value, multipliers, caps). Both server and client read these; add or change a unit/grave there only. The only client-only grave data is the image/emoji/color in `GameData.GRAVE_UI`.

**Client** (`src/client/init.client.lua` is a bootstrap that requires the modules in UI draw order). All UI is built in code (no StarterGui instances), parented to the one ScreenGui from `Modules/Gui`. `src/client/Modules/`:
- Foundations: `State` (client mirror of the server's data: `State.gold`, `State.inventory`, ... written ONLY by `Sync`), `Sync` (applies `DataSync` snapshots, refreshes the UI, `hold()`/`release()` to delay updates until a roll/wheel reveal, `onApplied(fn)` for panels), `GameData` (unit/grave display tables derived from `src/shared`), `Format`, `Gui`
- Older panels with `Module.init(screenGui, ctx)`: `GravesDock`, `InventoryPanel`, `ShopPanel`, `QuestsPanel`, `HUD`
- Newer modules that build their UI when required: `Toolbar` (hotbar with 3D portraits and level badges, tooltip, `refresh`; the selected unit is HELD in the hand as a scaled-down copy of its real model from `UnitModels`, a coloured block only for units without a model), `LevelBadge` (the "Lv N" plate on hotbar/inventory slots, gold at max), `UnitPortrait` (3D ViewportFrame portraits), `GachaReveal` (the overlay reveal), `StarSummon` (the sky cinematic for rare pulls), `ForgePanel` (upgrades), `Placement` (Place Best, SelectGrave -> PlaceAtGrave), `GraveRolling` (roll animation, `openGrave`), `Effects` (wall-break effects, `showBigText`), `HitEffects` (the hit flash on the wall for each `WallHit`: core flash, sparks, dust, light; the server puts it on the wall face right in front of the attacking unit at about chest height; there are no floating damage numbers), `SpellEffects` (staff casters, see below), `AscendPanel`, `SellPanel`, `UpgradePanel`, `WheelPanel`
- UI created later draws on top of earlier UI, so keep the require order in `init.client.lua`.

## Plot geometry (never assume an axis)

Plots point in different directions, so **never use world X/Z for lane math**. Each `plotState` has `frame` (CFrame at the plot's floor-level centre, LookVector = lane direction outward, RightVector = across), `wallFwd` (distance of the wall being fought from the centre; it advances as walls break), `wallTargetFwd`/`wallFaceFwd`. Use `Modules/PlotFrame`: `toWorld(plotState, lateral, forward)`, `toLocal(plotState, worldPos)` (returns lateral, forward), `rotation`, `forwardFlat`. Units keep their own `lateral` lane. Walls are oriented with the plot (part X = across, Z = thickness). `GetWallPos` returns a CFrame in front of the wall.

## Server authority and saving

- **The client never changes gold, gems, inventory, graves, upgrades or ascension.** It sends requests (BuyGraveRequest, DigGrave, PlaceAtGrave(invSlot, graveSlot), PlaceBest, SellUnit(invSlot), SwapInventory, BuyUpgrade, UpgradeUnit, DismantleUnit, PlayerAscend, WheelSpin, ClaimQuest); the server validates cost/ownership/limits and applies them via `PlayerData`. Any new feature that gives or takes currency/units must go through `PlayerData` on the server.
- Results come back as a full `DataSync` snapshot. Inventory is sent as a list of `{slot, unitType, oneIn, level, fails}` (sparse arrays don't survive remotes); it also carries `materials`, `placed` (units on graves) and `gateCleared`.
- Saved per player (`Persistence`, DataStore `PlayerData_v1`, key `player_<UserId>`): gold, gems, ascension, inventory (with unit levels), owned graves, upgrades, upgrade materials, pity, units placed on graves (with levels), wheel spins, quest progress. Autosaves every 60s, on leave and on shutdown. If a load fails the player gets defaults and is **never saved** that session (`profile.loadFailed`) so stored data can't be overwritten.
- DataStore does nothing in Studio unless "Enable Studio Access to API Services" is on (Game Settings > Security); without it every load fails and nothing is saved.
- Testing saves in Studio: the Stop button ends the session before the leave-save finishes, so only the 60s autosave (or `Player:Kick()` from a server `execute_luau`) is reliable there. Save logs `💾 saved data for <name>`.
- New players start with `START_GOLD = 300` in `PlayerData`.
- `/give <Unit>` debug chat command only works in Studio.
- **Formation** (`Army.layoutFormation`): the army does not stand where it likes. Each unit walks from its grave to a slot facing the wall: its **row** follows from its attack range (`Army.standDistance`: range up to 12 stands just inside its range, rounded down to a multiple of 5 and at least 1.5; beyond 12 every extra stud of range moves the unit 2.5 studs further back, so range 15 stands 15 studs from the wall, 20 -> 30, 25 -> 40, 30 -> 55: mages and archers fight from far away so their projectiles travel a long way; future artillery goes even further back) and inside a row units spread across the lane (4-7 studs apart by size, centre first then alternating right/left so arriving units never move the standing ones, every other row staggered). Slots (`u.slotLat`, `u.slotStand`) are recomputed whenever the number/ids of units in a plot change; a unit attacks once it has arrived (`ARRIVE_RADIUS`), and keeps attacking unless pushed further than `STAY_RADIUS`. The front wall advances after every break, so units march on to the next wall (and are sent back to the graves when the owner ascends).
- **Dev panel (Studio only)**: the purple `🛠 DEV` button on the left of the screen opens a list of every unit (client `Modules/DevPanel`); clicking one fires `DevSpawnUnit` and the server (`Modules/DevTools`, checks `RunService:IsStudio()`) spawns it at its formation row in front of your wall so it attacks right away, or (panel toggle `Spawn at: GRAVES`) at the graves so it marches in and you can watch the formation form. `Clear dev units` (`DevClearUnits`) removes them. Dev units are flagged `entry.dev`, are not tied to graves or the inventory and are never saved. Neither module does anything outside Studio.

## Economy and balance (tuned with a simulator)

`tools/sim/economy_sim.py` (Python, no dependencies) plays the game as a typical player in ACTIVE time and prints how long each ascension takes against the pace targets. It READS the real roster, odds tables and grave prices from `src/shared/*.lua`. Presets: `current` (the old formulas), `proposed` (gold-price ascension), `gate` (32 walls, beating the gate ascends, one material per rarity) and `dust` (what the game does now: `gate` with the five paired dusts and their shop). Run `python tools/sim/economy_sim.py --preset dust --runs 8 --max-hours 800`; `tools/sim/tune.py` / `tune_gate.py` try different per-ascension steps. **Change the numbers in the sim first, check the table, then copy them into `Economy.lua`/`Graves.lua`/`Units.lua`/`GraveShop.lua`.** Last result of the gate preset (median, active play): ascension 1 ~20 min, 2-4 ~15-20 min each, 5 ~45 min, 6 ~80 min, 7 ~4 h, 8 ~12 h, 9 ~25 h; all nine about 43 h = ~22 days at 2 h/day; without the upgrade system the same run takes ~104 h, so the Forge carries about half of the pacing. - **Rarity odds**: every grave has its own `odds` table (percent) in `Graves.lua` (a bell around a centre rank that rises with the tier; Primordial only in the top graves). `Rolling.rollRarity` picks from it; the luck upgrade (+10 % per level) and the wheel's 2x buff multiply the weights of Rare and better (`luckFactor`), pity (60 rolls without the grave's `pityRarity` or better = a guaranteed one). `Rarities.BaseOdds` is only used for the displayed "1 in X" (`Units.getBaseOneIn`) and the sell value. The UI shows "Best: Eldritch 0.68%" (`GameData` `bestRarity`). If paid pulls/boosters are ever sold, show the odds (Roblox rule).
- **Unit DPS** is geometric by rarity rank (~3.2x per step; Common ~10, Primordial ~110000), small differences inside a rarity (`Units.lua` `damage` / `attackCD`). Sigilwright 85000 DPS, Last Lantern 439805 damage per 4 s.
- **Walls** (`Economy.wallHp/wallGold`): HP = 300 x 1.22^(layer-1) x product of the per-ascension HP steps (3.5, 3.5, 3.5, 9, 6, 9, 8, 6, 6), the gate x1.5; gold = 45 x 1.12^(layer-1) x gold steps; coin boost multiplies wall and sell gold. **Ascension** = damage x1.5 each (`Economy.damageMultiplier`), no gold price, gold resets to 0. Grave prices Mossy 100, Stone 1.5K, Ancient 25K, Cursed 400K, Shadow 6M, Abyssal 100M, Eldritch 1.6B, Void 25B, Eternal 400B, Celestial 6T; shop stock per 5-minute restock Mossy 40, 25, 20, 15, 12, 8, 5, 3, 2, 1. New players start with 300 gold. Numbers format up to T / Qa.
- **Known balance gaps**: late game (ascension 8-9) has only ~1-2 progress events per hour (more upgrade levels for top rarities, level auras, mutations are the planned fillers); a player who spent everything on bad pulls can stall (ideas: "sell all spares" button, a minimum income per wall, lower pity on the first graves); sell value of spares is still `oneIn^1.2 * 5` (checked only inside the sim).

## Gacha reveal

`DigGrave(graveType, count)` (server `Digging.lua`) opens up to 10 graves in one request (stops when graves or inventory space run out) and answers with ONE `RollResult` carrying the list of results. Client `GraveRolling` hands the list to `Modules/GachaReveal.play(results, opts)`: an overlay (not full screen) with buildup (the grave shakes, a glow hints at the rarity, big rarities flicker out before the burst), burst (flash, rings, sparks, shake), reveal (a 3D `ViewportFrame` portrait of the unit on a plinth, name, rarity, odds, pity) and Collect. Skip jumps to the reveal. With several results the BEST one gets the dramatic reveal, then a grid of all of them (`Show all`), then `Open xN` for more. **Effects scale smoothly with the rarity rank** (`t = (rank-1)/(maxRank-1)`: buildup length, shake, sparks, rings, fake-out above t 0.55), there is no per-rarity special case, so new rarities work unchanged. Sounds: fill `GachaReveal.Sounds` (buildup, burst, reveal, rare, collect) with sound ids. The portraits need the unit models on the client: `ReplicatedStorage.UnitModels` (a copy of `ServerStorage.Models`, made by `tools/studio/publish_unit_models.lua`; **re-run it after changing or adding a unit model and save the place**). The DEV panel has `Reveal x1` / `Reveal x10` / `Rarity: ...` buttons to preview reveals without rolling. **Graves panel** (`Modules/GravesDock`, the module kept its old name so Sync/ShopPanel/WheelPanel keep calling `refresh()`): a small gold "Graves" stone button on the left (under Inventory) with a badge showing the total number of graves owned; click it or press G to open a stone panel with a card for every grave type (picture, name, count, locked ones show the ascension that unlocks them). Select a card, then `Open x1` or `Open xN` (N = min(10, owned)); the panel closes when an opening starts. Nothing is drawn in the middle of the screen otherwise. `Open all` is planned as a PAID feature: add it as a third button there. Ideas on hold: a 3D camera zoom into the real grave, a full-screen mode.

## Sell all and locks

The inventory panel's sidebar (`InventoryPanel`) has a SELL ALL section: a rarity button that cycles "up to" Common..Primordial, a "Keep Lv 1+" toggle (on by default), a live preview ("7 units / 345 Gold") and a red Sell button that asks "Sure?" first. Server `Inventory.lua` `SellAll(maxRank, keepUpgraded)` sells every unlocked inventory unit of that rank or lower (1 s rate limit) and answers with a Notice. "Lock mode" turns slot clicks into lock toggles (`ToggleLock`, `PlayerData.toggleLock`); a locked unit shows a gold LOCK tag, is saved with `locked = true` on its inventory entry and can never be sold (single or all) or dismantled. Units on graves are never touched; the lock travels with the unit onto a grave and back (`slot.locked`, `placeInSlot(..., locked)`, saved in `placed`).

## The Forge (unit upgrades and materials)

Units have a `level` (0..`Economy.MAX_UNIT_LEVEL` 10; +30 % damage per level, `Economy.levelMultiplier`) and a `fails` counter (failed upgrades in a row, the pity). They live on the inventory entries (`{ unitType, oneIn, level, fails }`) and on the grave slots (`slot.level`, `slot.fails`) and travel with the unit when it is placed (`PlaceAtGrave`, `Army.placeInSlot(plot, slot, unitType, level, fails)`), recalled, re-deployed by Place Best (which sorts by DPS including the level) and saved (`inventory`, `placed`, `materials` in `Persistence`). Damage of a spawned unit = base x ascension multiplier x level multiplier (`Army.spawnUnit`, `setDamageMultiplier`, `setUnitLevel`); the model gets the attribute `Level` (auras at level milestones are not built yet).

**Materials** are five DUSTS, one per pair of rarities (`Economy.DUSTS` / `DUST_NAMES`, saved under these keys): Stone Dust (Common, Uncommon), Silver Dust (Rare, Cursed), Gold Dust (Legendary, Abyssal), Diamond Dust (Eldritch, Eternal), Star Dust (Primordial; a future rarity above it could share it or get Cosmic Dust). `Economy.dustOf(rarity)` maps a rarity to its dust, `profile.materials[dust]`, `PlayerData.addMaterial/spendMaterial(player, dust, n)`. Old saves with one material per rarity are poured into the matching dust on load. Walls drop dust in `Walls.breakWall` (`Economy.wallMaterials` returns `{dust, amount}`: mostly the dust of rarity ascension + 2, boss walls (every 10th) and the gate add 3x of the dust of the rarity above); dismantling a spare inventory unit gives `Economy.dismantleYield(rank)` of its own dust. NOT built yet: the material shop (sim preset `dust`: 10 of each dust per 5-minute restock at 20 x 50^dustIndex gold), premium catalysts.

**Level auras** (client `Modules/LevelAuras.lua`, from the model attribute `Level`; every tier keeps the layers below and adds one, necromantic look, same for every unit): level 3 souls rising from a ring around the feet (NO visible ground circle, the user rejected it), 6 + three soul orbs with trails orbiting the body and a soft light, 9 + dark green necrotic flames (kept dim: LightEmission ~0.35) and black miasma, 10 + violet flame core, a crown of five small skulls circling above the head and a flash when reached. Sizes follow the unit's bounding box; auras exist only within 140 studs of the camera; no Highlights (31 per client limit). The DEV panel's `Lv` button spawns dev units at level 0/3/6/9/10 to preview them. The grave label shows `Unit  Lv N`; the HUD shows a dust row above Gold/Gems.

**Rules** (all in `Economy`, tuned with the sim): going from level L to L+1 costs `unitUpgradeCost(L, rarity)` = ceil(4 x 1.55^L) of the unit's dust (x1.5 for the higher rarity of a pair) and succeeds with `upgradeChance(L, fails)` = max(0.2, 1 - 0.08L) + 0.10 x fails (max 1). A failure costs half the materials, never lowers the level and raises the next chance. Server `Modules/UnitUpgrades.lua` handles `UpgradeUnit(kind "inv"|"grave", index)` and `DismantleUnit(invSlot)` (small rate limit), answers with `UpgradeResult(success, unitType, newLevel, chance)` and the usual DataSync (which now carries `materials` and `placed`; `PlayerData.placedProvider` is set by Army). Client `Modules/ForgePanel.lua` (opens ONLY at the Forge stall via `OpenForge`, closes when the player walks more than 22 studs away; there is no side button or F key any more, a premium "Remote Forge" may unlock that later; the server refuses UpgradeUnit/DismantleUnit unless `ShopNpcs.nearForge(player)`, 25 studs): list of units on graves + inventory, details, cost, chance, Upgrade/Dismantle, a row with all nine materials.

## Conventions

- Lua/Luau, tabs for indentation, `local function` for helpers, forward-declare locals that are used before they are defined.
- Section headers use `-- ====` banner comments. Keep that style in existing files.
- Player data is keyed by `tostring(player.UserId)`.
- Grave tiers: Mossy, Stone, Ancient, Cursed, Shadow, Abyssal, Eldritch, Void, Eternal, Celestial (one unlocked per ascension).
- Sell value: `Economy.sellValue(oneIn)` = `math.floor(oneIn ^ 1.2 * 5)`, times `1 + coinBoost * 0.5`. Wall gold: `Economy.wallGold(layer, rebirths)` times `1 + coinBoost * 0.5`. DPS: `damage / attackCD` times the ascension multiplier times the unit's level multiplier. Rarity rolls: see "Economy and balance".
- Rarity rolls use `math.random()` against the grave's odds table weights, so tiny odds like 0.001% work. Rarity order (low to high): Common, Uncommon, Rare, Cursed, Legendary, Abyssal, Eldritch, Eternal, Primordial.

## Roblox gotchas

- `Enum.KeyCode.BackQuote` does not exist, and `Tilde` may be intercepted by the console. Prefer a HUD button or `I`.
- Create **all** RemoteEvents/Functions at server startup. Lazily created remotes make client `WaitForChild` time out.
- **A local function or constant defined further down a file is nil inside code above it** (the call errors EVERY frame and freezes everything after it in that loop): this froze the Sigilwright bolts twice (`boltImpact`, `BOLT_ACCEL`). Forward-declare or define above. Also: do not weld child parts to an anchored part that is moved every frame (they stay behind): build moving effects from a single part.
- Forward-declare locals before functions that reference them (e.g. `local wheelPanel`). Numbers and strings are copied by value, so share them across modules via getters or a state table.
- `BodyVelocity`/`BodyGyro` are used for unit movement (deprecated but working).
